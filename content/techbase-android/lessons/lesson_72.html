adb and device commands

bash
adb devices                                  # list connected devices and emulators
adb install -r app/build/outputs/apk/debug/app-debug.apk   # install/replace an APK
adb uninstall com.example.marketmate         # remove an app
adb shell pm clear com.example.marketmate    # wipe app data (reset to first run)
adb shell am start -n com.example.marketmate/.MainActivity   # launch an activity
adb shell am force-stop com.example.marketmate               # kill the app
adb shell dumpsys activity activities | grep mResumed        # which activity is in front?
adb shell input text "hello"                 # type text; adb shell input keyevent 66 = Enter
adb shell screencap /sdcard/s.png && adb pull /sdcard/s.png  # screenshot
adb shell screenrecord /sdcard/demo.mp4      # record the screen (Ctrl+C to stop; adb pull to copy)
adb pull /sdcard/Download/file.txt .         # copy from device to computer
adb push local.txt /sdcard/Download/         # copy to device
adb tcpip 5555                               # restart adb in TCP mode (wireless debugging legacy)
adb pair <ip:port>                           # pair for Wireless debugging (Android 11+)
adb connect <ip:port>                        # connect after pairing
adb reverse tcp:8080 tcp:8080                # device reaches your laptop's localhost:8080
adb logcat -c                                # clear the log

(Emulator note: 10.0.2.2 is the emulator's name for your computer's localhost; lesson 4.)

Logcat

bash
adb logcat                                   # everything (very noisy)
adb logcat -s MyTag                          # only the tag "MyTag"
adb logcat *:E                               # errors and above
adb logcat --pid=$(adb shell pidof -s com.example.marketmate)   # one app only
adb logcat -d > log.txt                      # dump current log to a file and exit

implementation Needed to compile and run; hidden from consumers
api Exposed to consumers (libraries only)
ksp(...) Annotation processor (Room, Hilt)
testImplementation Local unit tests
androidTestImplementation Instrumented tests
debugImplementation Debug builds only (tooling)

Architecture on one page (lessons 60 to 65)

text
UI layer       Composable (stateless) ◄── UiState (immutable) ◄── ViewModel / state holder
                    │ events up                                       ▲
Domain layer   Use cases (optional, plain Kotlin)                     │ state down
Data layer     Repository (interface) ─► Local source (Room) / Remote source (Retrofit / Ktor)

Rules: state flows down, events flow up (UDF) | one source of truth (database) |
       dependencies point down | inject dependencies (Hilt) | fakes over mocks | main-safe suspend functions
Question Answer
Where does business logic live? Domain (use cases) or ViewModel; never in composables
Where do threads get chosen? In the data layer (inject dispatchers)
How do one-off events work? Model them as state and consume them (61)
How to persist small state across process death? SavedStateHandle / rememberSaveable
How to work offline? Room as source of truth + WorkManager sync (64)

Step-by-Step Build 5: Twenty Interview Questions

Try answering aloud before reading each answer. Keep answers short and specific, and give an example from your own projects.

🎯 Your Challenge

Interview set A (fundamentals). Answer in two or three sentences each: (1) What is the Activity lifecycle and why does it matter? (2) What is the difference between val and var? (3) What is a data class? (4) What is null safety in Kotlin? (5) What is a coroutine? (6) What is the difference between Flow and StateFlow? (7) What is a ViewModel and why use one?

(1) The lifecycle is the set of states (created, started, resumed, paused, stopped, destroyed) the system moves an Activity through; apps must acquire and release resources at the right states, and survive being recreated on rotation or killed in the background. (2) val is a read-only reference, var can be reassigned; prefer val. (3) A class that holds data and generates equals, hashCode, toString, copy and destructuring. (4) Types are non-null by default; ? makes them nullable, and the compiler forces safe handling via ?., ?: and checks. (5) A lightweight, suspendable unit of work managed in a scope, giving structured concurrency without blocking threads. (6) Flow is a cold stream of values; StateFlow is a hot flow that always holds a current value and replays it to new collectors. (7) A state holder that survives configuration changes, exposes UI state and handles business logic calls, keeping composables simple.

🎯 Your Challenge

Interview set B (Compose and UI). (8) What is recomposition? (9) What is state hoisting? (10) remember versus rememberSaveable? (11) Why use LazyColumn keys? (12) What is a side effect in Compose, and name two APIs? (13) How do you make a composable accessible?

(8) Re-running composables whose read state changed, skipping those whose inputs did not. (9) Moving state up to a caller, passing the value and an event callback down, so composables are stateless, reusable and testable. (10) remember keeps a value across recompositions; rememberSaveable also survives configuration changes and process death by saving to the saved-instance state. (11) Keys give items stable identity so reordering and insertions keep state and avoid unnecessary recomposition. (12) Work outside the composable's pure drawing, such as launching coroutines or registering listeners: LaunchedEffect, DisposableEffect, rememberCoroutineScope, SideEffect. (13) Content descriptions for meaningful images and icons, 48dp touch targets, sufficient contrast, semantics for custom components, support for font scaling and TalkBack testing.

🎯 Your Challenge

Interview set C (architecture, data, and tools). (14) Describe the recommended Android architecture. (15) What is a repository? (16) What does offline-first mean? (17) Why dependency injection? (18) How do you test a ViewModel? (19) What is R8 and why test release builds? (20) What would you share with Kotlin Multiplatform and what keep native?

(14) UI layer (composables plus state holders) driven by immutable UI state with unidirectional data flow, an optional domain layer of use cases, and a data layer of repositories over local and remote sources; dependencies point downward, with one source of truth. (15) A class that exposes data to the rest of the app, hides its sources, resolves conflicts between them and owns business rules about that data. (16) The local database is the source of truth; the UI reads it, writes go to it first, and the network syncs in the background, so the app works without connectivity. (17) Classes declare their dependencies rather than creating them, which improves testability, reuse and lifetime management; Hilt generates the wiring. (18) Construct it with fakes (not mocks), replace the main dispatcher with a test dispatcher, drive it with function calls, and assert on the emitted state with runTest. (19) R8 shrinks, optimises and obfuscates code; it can remove or rename classes that reflection needs, so release builds can crash where debug builds do not. (20) Share domain logic, models, repositories, networking and perhaps database; keep platform UI, notifications, biometrics and platform integrations native behind interfaces.

Questions to ask the interviewer

Good questions show care: How is the app architected today? How do you test and release? How do you measure crashes and performance? What does onboarding look like for a new Android developer? Is the code reviewed?

A study plan

Months 1 to 3: consolidate.

  • Rebuild two earlier apps from scratch without looking.
  • Complete the capstone (lesson 71) and publish it to an internal test track.
  • Read one codelab per week from the official Compose pathway you found hardest.
  • Write ten unit tests for code you did not test before.

Months 4 to 6: deepen.

  • Add offline-first sync with a real backend (Firebase or a simple REST API) to the capstone (lesson 64).
  • Learn Hilt and modularisation on a real project (lesson 65).
  • Do one performance pass with Macrobenchmark and a Baseline Profile (lesson 57).
  • Make the app adaptive and review accessibility with TalkBack (lessons 46 to 48 and 58).
  • Contribute a small fix or documentation improvement to an open-source Android project.

Months 7 to 12: specialise and ship.

  • Pick a direction: product apps, Wear OS and widgets (59), Kotlin Multiplatform (66 to 70), accessibility, performance, or testing and CI.
  • Publish a second app to production. Remember the Play account rules from lesson 53, including testing requirements for new personal accounts.
  • Write two short articles or talks about what you learned.
  • Build a portfolio site with links to your repositories, Play listings and write-ups.

Common Mistakes (and How to Fix Them)

Mistake #1: Memorising instead of building. Fix: use cheat sheets after practising, not instead of it.

Mistake #2: Collecting courses and never publishing. Fix: ship something small every quarter.

Mistake #3: Copying versions from old tutorials. Fix: look up the latest stable version.

Mistake #4: Claiming a certificate you do not hold. Fix: describe exactly what you completed and link it.

Mistake #5: Skipping tests because "it works on my phone". Fix: automate checks for rules and ViewModels.

Mistake #6: Ignoring accessibility and performance until the end. Fix: check them with every screen.

Mistake #7: Only studying alone. Fix: join a community, review others' code, ask questions.

Mistake #8: A portfolio of unfinished projects. Fix: finish fewer, better projects with READMEs.

Mistake #9: Never reading release notes. Fix: read the Compose and AGP notes before upgrading.

Mistake #10: Giving up after a hard week. Fix: shrink the task, and ask for help early.

Knowledge Check

Question 1. Which Google certificate for Android is currently offered through the Android courses page?

The Google Play Store Listing Certificate; the Associate Android Developer exam is retired.

Question 2. What is the best evidence of Android skill for a junior developer?

A published, tested, accessible app with a clear repository and README, together with open-source or community contributions.

Question 3. Which command lists dependencies in Gradle?

./gradlew app:dependencies.

Question 4. What does "state flows down, events flow up" describe?

Unidirectional data flow: UI renders state from a state holder and sends user actions upwards as events.

Question 5. Why date your notes with versions?

Android Studio, Compose and libraries change quickly, so knowing which versions your notes match tells you what to re-check.

1

2

Choose Git > Create Git Repository… (or VCS > Enable Version Control Integration in older versions), select the project folder, then open Git > Commit, tick every file, and write the message “Add Android lesson 72 project”.

4
