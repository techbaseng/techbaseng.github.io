Lesson Introduction

You have now met nearly everything the official Android programmes cover: Kotlin, Compose, state, navigation, data, architecture, testing, accessibility, performance, release and sharing code. The final step is to use it all together in one complete app that you can put in a portfolio, show to an employer, or publish.

This capstone follows the shape of the official programmes' final projects (for example My City and the architecture pathway's offline-first app) but the app itself is original. You will plan it, build it layer by layer, test it, review its accessibility, and prepare it for release. Pointers back to the lessons that taught each skill are given throughout, so you can revisit anything that feels rusty. The official pathways remain the reference: https://developer.android.com/courses.

By the end you will have:

  • A plan with user stories, screens and a data model.
  • An architecture with UI, domain and data layers, built on Room, a repository, ViewModels, Compose and type-safe Navigation.
  • An offline-first feature using the database as the source of truth.
  • Unit and UI tests that guard the important behaviour.
  • An accessibility review and a release checklist.
  • A portfolio README for the project.

Big idea: a capstone is not about the number of features. It is about finishing a small thing well and being able to explain every decision.

Phase 3 of 14
Phase 1: Choose and Plan the App

The app: MarketMate

Problem. Traders and households in Ibadan see prices of foodstuff change from market to market and from week to week (garri, rice, tomatoes, beans). People rely on memory or phone calls. MarketMate lets a user record prices they see at markets, browse and search them, see the price history of an item, and find the cheapest recent price. It works offline, because market stalls often have poor signal.

(You may choose a different original app, such as a school fee helper or a church-event planner. Keep the same shape: a list, a detail screen, a form, a database and a few rules.)

User stories

# As a... I want to... So that...
1 shopper add a price (item, market, amount, date) I remember what I saw
2 shopper see recent prices in a list and search by item I can find what I need
3 shopper open an item and see all its prices by market I can compare
4 shopper see which market is cheapest in the last 30 days I know where to buy
5 shopper delete a mistaken entry my data stays correct
6 any user use the app without internet I can record in the market
7 user with a screen reader or large text use every feature the app is inclusive

Screens

text
[Prices list] --(tap item)--> [Item detail: history + cheapest market]
     |
     +--(FAB)--> [Add price form]

Data model

text
PriceEntry
  id            Long (auto)
  itemName      String        "Garri (white, 1 paint bucket)"
  marketName    String        "Bodija"
  amountKobo    Long          money as whole kobo, never Double
  recordedAtMs  Long          epoch millis

Rules (the domain)

  • Amount must be greater than zero.
  • Item and market names are trimmed and must not be blank.
  • "Cheapest market" = the market with the lowest average price for the item in the last 30 days; ties are broken alphabetically.

Non-functional requirements

Works offline; no network needed in version 1; supports dark mode and font scaling; every control has at least a 48dp touch target; every icon has a content description or is decorative.

Checkpoint (lessons 60 to 63): which parts are UI, domain and data? UI: three screens and ViewModels. Domain: validation and the cheapest-market rule. Data: Room and the repository.

Repository

kotlin
// data/PriceRepository.kt
interface PriceRepository {
    fun observeAll(): Flow<List<PriceEntry>>
    fun observeForItem(item: String): Flow<List<PriceEntry>>
    suspend fun add(item: String, market: String, amountKobo: Long, recordedAtMs: Long)
    suspend fun delete(id: Long)
}

class OfflinePriceRepository @Inject constructor(
    private val dao: PriceDao,
    @IoDispatcher private val io: CoroutineDispatcher
) : PriceRepository {

    override fun observeAll() = dao.observeAll()
        .map { list -> list.map { it.toModel() } }
        .flowOn(io)

    override fun observeForItem(item: String) = dao.observeForItem(item)
        .map { list -> list.map { it.toModel() } }
        .flowOn(io)

    override suspend fun add(item: String, market: String, amountKobo: Long, recordedAtMs: Long) =
        withContext(io) {
            dao.insert(PriceEntryEntity(itemName = item, marketName = market,
                amountKobo = amountKobo, recordedAtMs = recordedAtMs))
        }

    override suspend fun delete(id: Long) = withContext(io) { dao.delete(id) }
}

Validation

kotlin
// domain/ValidatePrice.kt
sealed interface ValidationResult {
    data class Valid(val item: String, val market: String, val amountKobo: Long) : ValidationResult
    data class Invalid(val itemError: String? = null, val marketError: String? = null, val amountError: String? = null) : ValidationResult
}

class ValidatePriceUseCase @Inject constructor() {
    operator fun invoke(item: String, market: String, amountText: String): ValidationResult {
        val cleanItem = item.trim()
        val cleanMarket = market.trim()
        val naira = amountText.trim().toDoubleOrNull()

        val itemError = if (cleanItem.isEmpty()) "Enter the item" else null
        val marketError = if (cleanMarket.isEmpty()) "Enter the market" else null
        val amountError = when {
            naira == null -> "Enter a number"
            naira <= 0.0 -> "Amount must be more than zero"
            else -> null
        }

        return if (itemError == null && marketError == null && amountError == null) {
            ValidationResult.Valid(cleanItem, cleanMarket, Math.round(naira!! * 100))
        } else {
            ValidationResult.Invalid(itemError, marketError, amountError)
        }
    }
}

The cheapest-market rule

kotlin
// domain/CheapestMarket.kt
data class MarketAverage(val market: String, val averageKobo: Long, val samples: Int)

class FindCheapestMarketUseCase @Inject constructor() {
    operator fun invoke(entries: List<PriceEntry>, now: Instant, days: Long = 30): MarketAverage? {
        val cutoff = now.minus(days, ChronoUnit.DAYS)
        return entries
            .filter { it.recordedAt >= cutoff }
            .groupBy { it.marketName }
            .map { (market, list) ->
                MarketAverage(market, list.sumOf { it.amountKobo } / list.size, list.size)
            }
            .minWithOrNull(compareBy<MarketAverage> { it.averageKobo }.thenBy { it.market })
    }
}

now is a parameter, not Instant.now(), so the rule can be tested with fixed dates (lesson 63).

data class ListUiState(

@HiltViewModel
class ListViewModel @Inject constructor(
    private val repository: PriceRepository,
    private val savedState: SavedStateHandle
) : ViewModel() {

    private val query = savedState.getStateFlow("query", "")

    val uiState: StateFlow<ListUiState> =
        combine(repository.observeAll(), query) { entries, q ->
            ListUiState(
                query = q,
                entries = entries.filter { it.itemName.contains(q, ignoreCase = true) },
                loading = false
            )
        }.stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), ListUiState())

    fun onQueryChange(value: String) { savedState["query"] = value }
    fun delete(id: Long) { viewModelScope.launch { repository.delete(id) } }
}

State and ViewModel

kotlin
data class AddUiState(
    val item: String = "",
    val market: String = "",
    val amount: String = "",
    val errors: ValidationResult.Invalid? = null,
    val saved: Boolean = false
)

@HiltViewModel
class AddViewModel @Inject constructor(
    private val repository: PriceRepository,
    private val validate: ValidatePriceUseCase
) : ViewModel() {

    private val _state = MutableStateFlow(AddUiState())
    val state: StateFlow<AddUiState> = _state.asStateFlow()

    fun onItem(v: String) = _state.update { it.copy(item = v, errors = null) }
    fun onMarket(v: String) = _state.update { it.copy(market = v, errors = null) }
    fun onAmount(v: String) = _state.update { it.copy(amount = v, errors = null) }

    fun save() {
        val s = _state.value
        when (val result = validate(s.item, s.market, s.amount)) {
            is ValidationResult.Invalid -> _state.update { it.copy(errors = result) }
            is ValidationResult.Valid -> viewModelScope.launch {
                repository.add(result.item, result.market, result.amountKobo, System.currentTimeMillis())
                _state.update { it.copy(saved = true) }
            }
        }
    }
}

Accessibility review (lessons 46 to 48)

Run through this checklist and fix everything you find:

  1. TalkBack: every action reachable; announcements are meaningful ("Delete Garri at ₦2,500", not "button").
  2. Touch targets: at least 48dp (the delete icon button is; check custom controls).
  3. Font scale 200%: nothing truncated or overlapping; the list rows grow.
  4. Colour contrast: text and error states meet contrast guidance, in light and dark themes.
  5. Not colour alone: errors show text, not only red.
  6. Focus order and keyboard: Tab moves in reading order; IME action "Next" moves between fields.
  7. Accessibility Scanner and Compose accessibility checks in tests (lesson 48): zero warnings, or each one explained.

Performance review (lesson 57)

List uses key = { it.id }; no heavy work in composables (formatting is cheap; if lists grow, remember formatted strings or format in the ViewModel); build a release variant and scroll a 1,000-row list on a low-end device or emulator; add a Baseline Profile if start-up matters.

Phase 11 of 14
Explain Your Decisions

A capstone is only valuable if you can defend it. Before you call the project finished, imagine an interviewer or a teammate reading your repository for the first time, and prepare short, honest answers to the questions below. Writing them down also becomes the "Architecture" section of your README.

Why is the database the source of truth? Because the app must work with no signal in the market. The UI reads only from Room through a Flow, so a new entry appears instantly, and there is no second copy of the data that can disagree with the first (lesson 60).

Why does money use whole kobo? Floating-point numbers cannot represent many decimal amounts exactly, so repeated arithmetic drifts. Whole units are exact. The Double in the domain model exists only for display, and is derived, never stored.

Why are there use cases for such small rules? Validation and the cheapest-market rule are the parts most likely to change and most worth testing. Moving them out of the ViewModel means they are plain Kotlin that runs in milliseconds, and the ViewModel stays short (lesson 63). If a rule is trivial, you may decide a use case is overkill; the skill is making that call deliberately.

Why SavedStateHandle for the search query? The ViewModel survives rotation but not process death. The query is small and cheap to save, so it survives both, while the big data is reloaded from the database (lesson 61).

Why type-safe routes? A route is a Kotlin type, so the compiler checks the arguments, and a typo in a string cannot send the app to a missing screen (lesson 55).

What would you do differently with a server? Keep the database as the source of truth, add a remote data source, and a sync worker with WorkManager, as in lesson 64. The UI and domain layers would not change, which is the evidence that the layering worked.

What are the limits of this app? There is no cloud backup, no user accounts, no price validation against outliers, and no unit conversion between "paint bucket" and "kilogram". Naming limits honestly shows maturity. Choose one limit and write how you would address it.

If you cannot answer one of these questions, return to the lesson named in brackets, change the code or your understanding, and then continue.

Phase 13 of 14
Common Mistakes (and How to Fix Them)

Mistake #1: Starting with the UI before the data and rules are tested. Fix: build and test bottom-up, as in Phases 3 and 4.

Mistake #2: A bigger scope than you can finish. Fix: cut features, not quality.

Mistake #3: Money in Double. Fix: whole kobo, with Double only for display.

Mistake #4: Calling Instant.now() inside rules. Fix: pass now in.

Mistake #5: Logic in composables. Fix: move it to use cases and ViewModels.

Mistake #6: Testing only the happy path. Fix: test blank, zero, boundaries.

Mistake #7: Leaving accessibility to the end. Fix: review each screen as you finish it.

Mistake #8: Testing only debug builds. Fix: run the release build before publishing.

Mistake #9: No README or screenshots. Fix: treat presentation as part of the work.

Mistake #10: Copying code you do not understand. Fix: explain each layer in your own words (the "Explain Your Decisions" phase).

Phase 14 of 14
Knowledge Check

Question 1. Why is now passed as a parameter to the cheapest-market use case?

So the rule is deterministic and can be tested with fixed dates.

Question 2. Where does validation belong?

In the domain layer as a use case, with the ViewModel showing the resulting errors.

Question 3. Why does the list screen read from Room via Flow rather than refresh manually?

Room re-emits when the table changes, so the UI updates automatically from a single source of truth.

Question 4. Name two accessibility checks for the form screen.

Errors shown as text (not colour alone), labelled fields, 48dp touch targets, TalkBack announcements, and correct behaviour at large font sizes.

Question 5. What should you test before publishing?

The minified release build on a real device, including database operations and navigation.

class OfflinePriceRepositoryTest {
    private lateinit var db: MarketDatabase

    @Before fun setUp() {
        db = Room.inMemoryDatabaseBuilder<MarketDatabase>(ApplicationProvider.getApplicationContext())
            .setDriver(AndroidSQLiteDriver())
            .build()
    }
    @After fun tearDown() = db.close()

    @Test
    fun add_then_observe_returns_the_entry() = runTest {
        val repo = OfflinePriceRepository(db.priceDao(), StandardTestDispatcher(testScheduler))
        repo.add("Garri", "Bodija", 250_000, 1_000)
        val all = repo.observeAll().first()
        assertEquals("Garri", all.single().itemName)
        assertEquals(250_000, all.single().amountKobo)
    }
}
