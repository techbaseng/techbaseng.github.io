Lesson Introduction

Welcome to one of the most important lessons in the whole course. Today you learn the single idea that makes every Compose app work: state.

Picture a shop assistant with a notepad. Every customer who walks in sees whatever is written on the notepad's front page: today's price of garri. When the price changes, the assistant crosses out the old number and writes the new one, and from then on every customer sees the new number. In Compose, the notepad value is state, and the act of showing it again is recomposition. Once this picture is firmly in your head, text fields, switches, counters, shopping carts and even whole games become variations on the same theme.

By the end of this lesson you will be able to:

  • Explain what state is and how a change in state triggers recomposition.
  • Use remember and mutableStateOf, and explain why rememberSaveable survives screen rotation.
  • Build a text input with OutlinedTextField and control the on-screen keyboard with KeyboardOptions.
  • Add a Switch and connect it to state.
  • Apply state hoisting to make stateless, reusable, testable composables.
  • Format money with NumberFormat.getCurrencyInstance().
  • Build a complete Tip Calculator app, including a custom tip percentage.
  • Apply everything to the Art Space project: an original gallery app with images, buttons and state.

How this fits the bigger picture: This lesson covers the official Unit 2, Pathway 3 items of Android Basics with Compose: Understanding state in Compose, Intro to tip calculator, Intro to state in Compose, Calculate a custom tip, and the Project: Create an Art Space app. We follow the official order but write our own code, explain the "why" in more depth, and set up the code so that lesson 20 can test it.

Phase 2 of 11
Prerequisite Concepts

1. Composable functions (lessons 15 and 16)

A composable function is a Kotlin function marked @Composable that describes a piece of UI. It describes the screen; it does not draw pixels directly. Rows, Columns, Text and Image are all composables.

2. Buttons and lambdas (lesson 17)

Button(onClick = { ... }) { Text("Roll") } takes a lambda, a block of code stored to run later. You saw in lesson 12 that lambdas can be passed to functions. State hoisting is entirely about passing lambdas up and values down.

3. val and var (lesson 7)

val cannot be reassigned; var can. State values are declared with var because they change.

4. Default arguments and named parameters (lesson 8)

You will meet functions like calculateTip(amount, tipPercent = 15.0). A default means the caller may leave an argument out.

5. Nullable types and toDoubleOrNull() (lesson 10)

A text field gives you a String, but the user might type nothing or type 1.2.3. "12.5".toDoubleOrNull() gives 12.5, while "abc".toDoubleOrNull() gives null. The Elvis operator ?: supplies a fallback: value.toDoubleOrNull() ?: 0.0.

Phase 3 of 11
Conceptual Understanding: State and Recomposition

What is state?

State is any value that can change over time and that the screen depends on. A counter's number, the text typed into a field, whether a switch is on, the index of the picture being shown: all of these are state.

Not everything is state. The words "Calculate Tip" on a label never change, so they are just fixed data.

Why a plain variable does not work

Beginners often try this:

kotlin
import androidx.compose.material3.Button
import androidx.compose.material3.Text
import androidx.compose.runtime.Composable

@Composable
fun BrokenCounter() {
    var count = 0                       // plain variable, NOT state
    Button(onClick = { count++ }) {
        Text("Clicked $count times")
    }
}

Tap the button and nothing changes on screen. There are two separate reasons:

  1. Compose has no idea that count changed, so it does not redraw the button.
  2. Even if it did redraw, the function would run again from the top and var count = 0 would reset the number to zero.

The Compose cycle

Compose apps follow a three-step loop. Learn it by heart:

text
        +-----------------------------+
        |   1. EVENT                  |
        |   The user taps, types,     |
        |   slides a switch...        |
        +--------------+--------------+
                       |
                       v
        +-----------------------------+
        |   2. UPDATE STATE           |
        |   Your code changes a       |
        |   state value.              |
        +--------------+--------------+
                       |
                       v
        +-----------------------------+
        |   3. DISPLAY                |
        |   Compose re-runs ONLY the  |
        |   composables that read     |
        |   that state (recomposition)|
        +--------------+--------------+
                       |
                       +--------> back to 1 when the user acts again

Key vocabulary

Term Meaning Analogy
State A value that can change and affects the UI. The price written on the shop notepad.
Composition The first time Compose builds the UI from your composables. Opening the shop and writing everything out.
Recomposition Compose running composables again because state they read has changed. Crossing out the old price and rewriting it.
MutableState An observable box that holds a value and tells Compose when it changes. A notepad that rings a bell when edited.
remember Keeps a value alive across recompositions. The notepad does not get thrown away every time you glance at it.
rememberSaveable Like remember, but also survives rotation and some other changes. A notepad saved in a drawer overnight.

Compose is smart about recomposition: it only re-runs the pieces that actually read the changed state, not the whole screen. Because recomposition can happen often and in any order, composable functions must be fast and free of side effects such as saving files or changing unrelated variables. Lesson 37 returns to this in depth.

The three ingredients of state in code

kotlin
import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.remember
import androidx.compose.runtime.setValue

var count by remember { mutableStateOf(0) }

Read it from the inside out:

  • mutableStateOf(0) creates the observable box with the starting value 0.
  • remember { ... } stores that box so the next recomposition finds the same box instead of making a new one.
  • by is a property delegate. It lets you write count and count++ instead of count.value and count.value++. It needs the two imports getValue and setValue, which Android Studio offers when you press Alt + Enter on a red by.

Think about it: Why must remember wrap mutableStateOf? Because without it, every recomposition would run mutableStateOf(0) again and create a brand-new box holding 0, wiping the user's progress.

import androidx.compose.runtime.setValue
import androidx.compose.ui.Modifier
import androidx.compose.ui.unit.dp

class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {
            MaterialTheme {
                Surface(modifier = Modifier.fillMaxSize()) {
                    Column(modifier = Modifier.padding(24.dp)) {
                        RememberCounter()
                        SavedCounter()
                    }
                }
            }
        }
    }
}

@Composable
fun RememberCounter() {
    var count by remember { mutableIntStateOf(0) }
    Log.d("StateLab", "RememberCounter composed, count=$count")
    Button(onClick = { count++ }) {
        Text("remember: $count")
    }
}

@Composable
fun SavedCounter() {
    var count by rememberSaveable { mutableIntStateOf(0) }
    Log.d("StateLab", "SavedCounter composed, count=$count")
    Button(onClick = { count++ }) {
        Text("rememberSaveable: $count")
    }
}

mutableIntStateOf is a version of mutableStateOf made for Int, which avoids boxing numbers. Either works; use mutableStateOf(0) if you prefer.

Run it and watch

  1. Tap each button three times. Both show 3.
  2. Open Logcat (lesson 18) and filter with tag:StateLab. Every tap prints a fresh composed line. That is recomposition happening in front of you. Notice that tapping the first button does not necessarily re-log the second one, because only the composable that read the changed value recomposes.
  3. Rotate the emulator (the rotate icons beside the emulator, or Ctrl + Left Arrow). The remember button goes back to 0. The rememberSaveable button keeps 3.

If auto-rotate is off on your emulator, switch it on in the quick settings or the emulator side bar.

Why the difference?

Rotating the phone is a configuration change. By default Android destroys and recreates the activity, and remember lives inside the activity's composition, so it is thrown away. rememberSaveable additionally writes the value into a small bundle that Android hands back to the new activity. Lesson 23 explains the activity lifecycle behind this. For now:

Tool Survives recomposition Survives rotation Survives process death*
plain var No No No
remember Yes No No
rememberSaveable Yes Yes Usually yes, for small values

*When Android silently kills your app in the background to free memory and later restores it. Only small, simple values (numbers, text, booleans) belong in rememberSaveable.

Rule of thumb: for anything the user typed or chose, use rememberSaveable. Nobody wants to lose a half-typed bill amount because they turned their phone sideways.

Write the calculation first

A good habit: write the logic as a plain Kotlin function with no Compose in it. Plain functions are easy to reason about and, in lesson 20, easy to test. Create a new Kotlin file TipCalculator.kt in the com.techbase.tiptime package:

TipCalculator.kt
package com.techbase.tiptime

import java.text.NumberFormat
import kotlin.math.ceil

/**
 * Returns the tip as a number.
 * @param amount the bill before tip
 * @param tipPercent the tip as a percentage, for example 15.0 means 15 percent
 * @param roundUp when true, the tip is rounded UP to the next whole unit
 */
fun calculateTip(
    amount: Double,
    tipPercent: Double = 15.0,
    roundUp: Boolean = false
): Double {
    val tip = tipPercent / 100 * amount
    return if (roundUp) ceil(tip) else tip
}

/** Turns a number into money text using the phone's own currency settings. */
fun formatCurrency(value: Double): String {
    return NumberFormat.getCurrencyInstance().format(value)
}

Let us walk through it:

  • The default tipPercent = 15.0 means calculateTip(1000.0) works and gives 150.0.
  • ceil(tip) from kotlin.math rounds up to the next whole number. A tip of 12.5 becomes 13.0.
  • NumberFormat.getCurrencyInstance() produces money text using the phone's region settings: the currency symbol, the decimal separator and the grouping. A phone set to the US shows $150.00; a phone set to Nigeria typically shows ₦150.00. The exact symbol depends on the device's locale data, so the output on your emulator may differ from the examples here.

Some quick mental checks, which you will turn into real tests in lesson 20:

Call Result
calculateTip(1000.0) 150.0
calculateTip(1000.0, 20.0) 200.0
calculateTip(50.0, 15.0, roundUp = true) ceil(7.5) which is 8.0
calculateTip(0.0) 0.0

    val amount = amountInput.toDoubleOrNull() ?: 0.0

        verticalArrangement = Arrangement.Center

            modifier = Modifier

                .align(alignment = Alignment.Start),
            style = MaterialTheme.typography.headlineSmall

            value = amountInput,
            onValueChange = { amountInput = it },
            label = { Text(stringResource(R.string.bill_amount)) },

            style = MaterialTheme.typography.displaySmall
        )
        Spacer(modifier = Modifier.height(150.dp))
    }

How it works, line by line

  1. var amountInput by rememberSaveable { mutableStateOf("") } is the notepad value. It starts as an empty string, and it survives rotation.
  2. OutlinedTextField(value = amountInput, onValueChange = { amountInput = it }, ...). This is the cycle in miniature: - Display: the field shows whatever value is. - Event: when the user types, the field does not change itself. It calls onValueChange with the text it would like to show. - Update: your lambda stores that text in amountInput. - Display again: the change triggers recomposition and the field is redrawn with the new value.

A Compose TextField is a controlled component: it is only ever as up-to-date as the state you give it. If you forget the assignment amountInput = it, typing appears to do nothing. 3. amountInput.toDoubleOrNull() ?: 0.0 turns the text into a number safely. Empty text gives 0.0, so the screen shows a zero tip instead of crashing. 4. tip is computed during composition from amount. Because amount depends on amountInput, which is state, the tip recalculates automatically each time. You never write "update the tip label" code. You describe how the tip is derived from state and Compose does the rest. 5. KeyboardOptions(keyboardType = KeyboardType.Number) asks the phone to open the numeric keyboard. It is a request, not a guarantee, and it does not stop someone pasting letters, which is why we use toDoubleOrNull(). 6. singleLine = true keeps the field to one line. 7. Modifier.statusBarsPadding() stops content hiding under the status bar when the app draws edge to edge, and verticalScroll lets the layout scroll when the keyboard shrinks the available space.

Keyboard options in more detail

KeyboardOptions has several useful settings:

Setting Example Effect
keyboardType KeyboardType.Number, Text, Email, Phone, Decimal Chooses the keyboard layout. Decimal suits money because it offers a decimal point.
imeAction ImeAction.Next, ImeAction.Done, ImeAction.Search Changes the action key at the bottom-right of the keyboard.
capitalization KeyboardCapitalization.Words Capitalises automatically.

Use KeyboardType.Decimal or KeyboardType.Number for amounts. We will use Number for consistency with the official app, and you may prefer Decimal in your own work.

Tip: If you see Unresolved reference: KeyboardOptions, the import is androidx.compose.foundation.text.KeyboardOptions. It is in the foundation package, not material3. The same goes for KeyboardType, which lives in androidx.compose.ui.text.input.

Tip Calculator, Step 3: State Hoisting, Custom Tip and the Switch

Our screen works, but everything is crammed into one function. To add a second field and a switch cleanly, we apply the most important Compose design pattern.

What is state hoisting?

State hoisting means moving state up out of a composable, to its caller, so that the composable itself becomes stateless. A stateless composable follows one rule:

State flows down, events flow up.

text
   TipTimeLayout   (OWNS the state)
        |   ^
 value  |   |  onValueChange(newText)
 (down) v   |  (up)
   EditNumberField   (STATELESS: just shows the value
                      and reports what the user did)

Why bother?

Benefit Explanation
Reusable One EditNumberField serves both the bill and the tip percentage.
Testable A stateless composable can be tested by simply handing it values (lesson 20).
Single source of truth Exactly one place owns each value, so two parts of the screen cannot disagree.
Previewable You can preview it in Android Studio with any fake value.

The usual pattern: a composable that needs state takes two parameters, value: T and onValueChange: (T) -> Unit.

Walking through the new pieces

  • Three pieces of state live in TipTimeLayout: the bill text, the tip percentage text and the switch position. The two number fields keep their values as String because that is what a text field edits; we convert to numbers only when calculating.
  • EditNumberField has no state of its own. It takes value and onValueChange and hands both straight to the field. We use it twice with different labels.
  • @StringRes label: Int is an annotation that tells Android Studio "this Int must be the id of a string resource". If you accidentally pass R.drawable.something, Android Studio flags the error. You will use @DrawableRes in the same way later in this lesson and in lesson 21.
  • imeAction: the bill field shows a Next key that moves to the tip field, and the tip field shows Done, which closes the keyboard. Next and Done work by default for focus movement in simple forms; for custom behaviour you would add keyboardActions, which is beyond this lesson.
  • Switch(checked = roundUp, onCheckedChange = onRoundUpChanged): the same pattern as the text field. The switch does not flip itself; it reports the wanted new value and your state decides.
  • RoundTheTipRow sets the row height to 48.dp, a standard minimum touch target size, so the switch is easy to tap. Accessibility is covered in lessons 46 to 48.

(empty) 15 off $0.00

Type 50, 15, then turn the switch on and off and watch $8.00 change to $7.50. Rotate the phone: all three values survive because they are rememberSaveable.

Why hoisting where we did?

We could have hoisted state all the way up into a ViewModel. For a small screen like this, holding state in the top-level composable is the right size. In lesson 24 you will move state into a ViewModel when it grows or must survive more than the screen does.

How the gallery works

  • One piece of state, index, decides everything. artworks[index] is the current artwork, and the two stateless composables ArtworkFrame and ArtworkCaption simply draw whatever artwork they are given. That is state hoisting again: they own nothing.
  • Wrap-around arithmetic. (index + 1) % artworks.size goes 0, 1, 2, 0, 1, .... The % (remainder) operator makes the number loop back to zero after the last picture. For Previous we add artworks.size first, because in Kotlin -1 % 3 is -1, which is not a valid index; (0 - 1 + 3) % 3 is 2, the last picture.
  • Modifier.weight(1f) makes the picture frame take all the leftover space, pushing the caption and buttons to the bottom.
  • ContentScale.Fit shrinks the picture to fit without cropping. Crop would fill the frame but cut off the edges.
  • safeDrawingPadding() keeps the content clear of the status bar, navigation bar and cut-outs when the app draws edge to edge.
  • painterResource(art.image) loads a drawable by its id. The contentDescription comes from a string resource, never a hard-coded one.

Exercise 3: Favourite artworks

In Art Space, add a Favourite Switch under the caption. Each artwork must remember its own favourite setting while you move around the gallery. Hint: one Boolean is not enough. You need state per artwork.

Keep a set of favourite indexes in state. Using a Set<Int> is simple, and saving it with rememberSaveable works if you store it as a list of ints:

kotlin
import androidx.compose.material3.Switch
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.saveable.rememberSaveable

// inside ArtSpaceApp, next to `index`
var favourites by rememberSaveable { mutableStateOf(listOf<Int>()) }
val isFavourite = index in favourites

// below ArtworkCaption(art = art)
Row(verticalAlignment = Alignment.CenterVertically) {
    Text("Favourite")
    Switch(
        checked = isFavourite,
        onCheckedChange = { wanted ->
            favourites = if (wanted) favourites + index else favourites - index
        }
    )
}

favourites + index and favourites - index create new lists (Kotlin's List is read-only), and replacing the whole list is what notifies Compose of the change. rememberSaveable can store a list of Int because it is a type Android's Bundle understands. Add Row and Alignment imports if Studio asks.

Common Beginner Mistakes (and How to Fix Them)

Mistake #1: A plain variable instead of state. The wrong code: var count = 0 inside a composable. The result: the UI never updates and the value resets on any recomposition. The fix: var count by remember { mutableStateOf(0) }.

Mistake #2: mutableStateOf without remember. The wrong code: var count by mutableStateOf(0). The problem: a fresh box is created on every recomposition, so the value always snaps back to 0. The fix: wrap it in remember (or rememberSaveable).

Mistake #3: Red by keyword. The error: Property delegate must have a 'getValue(...)' method. The fix: add import androidx.compose.runtime.getValue and import androidx.compose.runtime.setValue. Press Alt + Enter on the red text.

Mistake #4: A text field that will not change. The wrong code: OutlinedTextField(value = "", onValueChange = {}, ...). The problem: the field shows exactly the value you pass, and you never update it. The fix: store the new text in state: onValueChange = { text = it }.

Mistake #5: Using remember for user input and losing it on rotation. The symptom: typed text vanishes when the screen turns. The fix: rememberSaveable.

Mistake #6: Converting text to a number with toDouble(). The wrong code: amountInput.toDouble(). The problem: an empty string throws a NumberFormatException and the app crashes (read the stack trace using lesson 18). The fix: toDoubleOrNull() ?: 0.0.

Mistake #7: Hard-coded strings. The wrong code: Text("Calculate Tip"). The fix: put the words in strings.xml and use stringResource(R.string.calculate_tip) so the app can be translated and the words live in one place.

Mistake #8: Hiding state inside reusable composables. The problem: if EditNumberField owned its own remember, the parent could not read the text, and two fields could not be coordinated. The fix: hoist state to the caller and pass value plus onValueChange.

Mistake #9: Forgetting contentDescription. The problem: screen readers say nothing useful about your images. The fix: always give meaningful descriptions for pictures that carry meaning (use null only for purely decorative images).

Mistake #10: Index arithmetic that goes out of range. The wrong code: index = index + 1 in Next. The problem: past the last picture the app crashes with an index-out-of-bounds exception. The fix: use % artworks.size, or stop at the end.

Phase 11 of 11
Knowledge Check

Question 1. What is state in a Compose app, and what happens when it changes?

State is any value that can change over time and that the UI depends on. When a MutableState value changes, Compose schedules recomposition: it re-runs the composables that read that value so the screen shows the new value.

Question 2. Why is var count = 0 inside a composable not a good way to keep a counter?

Compose cannot observe a plain variable, so it will not redraw when it changes, and the composable function re-runs from the top and resets it to 0. State needs mutableStateOf (so Compose observes it) wrapped in remember (so it survives recomposition).

Question 3. What is the difference between remember and rememberSaveable?

remember keeps a value across recompositions but loses it when the activity is recreated, for example on rotation. rememberSaveable also stores the value in saved instance state, so it survives configuration changes and usually process death too, as long as the value is a type that can be saved to a Bundle.

Question 4. Describe state hoisting and the two parameters a hoisted composable normally has.

State hoisting moves state out of a composable into its caller, making the composable stateless. It receives the current value and an onValueChange: (T) -> Unit callback. State flows down; events flow up. Benefits are reuse, easier testing and a single source of truth.

Question 5. In Art Space, why does the code use (index + 1) % artworks.size rather than index + 1?

The remainder operator wraps the index back to 0 after the last artwork, so the user can keep pressing Next without the app trying to read a non-existent item, which would crash with an index-out-of-bounds exception.
